# EnterpriseOS API

The five-phase implementation uses a Java 25 Spring Boot application, MySQL 8.4, JDBC and Flyway. Schema migrations run on startup. Existing databases are never auto-rebuilt. Use an empty database for the first run. Exact feature coverage and remaining gaps are tracked in `docs/phase3-coverage.csv` and `docs/phase4-5-coverage.csv` at the repository root.

Build from this directory with Java 25 and Maven 3.9+: `mvn verify`. Integration tests use a real MySQL 8.4 container through Testcontainers, or an explicitly configured isolated test database through `TEST_DB_URL`, `TEST_DB_USERNAME`, and `TEST_DB_PASSWORD`. Test rows use unique IDs and remain in that test database; never point it at production. Without either Docker or an explicit test database the integration suites are skipped; a successful compile alone does not verify MySQL behavior. Start with `mvn spring-boot:run` after setting `DB_URL`, `DB_USERNAME` and `DB_PASSWORD`. The database account must be able to apply the supplied migrations in development. A separate migration account is appropriate for production.

Set `APP_PUBLIC_BASE_URL` to the browser frontend URL. The frontend proxies `/api` to this backend. Mutating requests require an exact allowed `Origin`; list browser origins in `APP_ALLOWED_ORIGINS` as comma-separated absolute origins. CORS is intentionally disabled. A command-line API request must include an allowed `Origin` header too. Configure HTTPS and `APP_SECURE_COOKIES=true` for deployment. Local HTTP development uses `false`. `APP_SESSION_HOURS` defaults to 8 and is capped at 24. Opaque session tokens are only stored in the HttpOnly, SameSite=Lax `EOS_SESSION` cookie; the database stores their SHA-256 hashes. All authenticated requests re-read active membership, current role and tenant status. Deactivation, password reset and suspension revoke relevant sessions.

No sample business records or default passwords are created. The native launcher starts an empty installation and enables the first-run setup screen, which creates the real company owner and a separate platform administrator using privately entered passwords. Setup is guarded by a database lock and is unavailable after initialization. See the root `docs/OPERATIONS.md` for startup, configuration and backup instructions.

Email is transactional: invitations/reset requests commit a delivery job alongside business changes. With `SMTP_HOST` configured, the worker sends through `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_AUTH` and `SMTP_STARTTLS`; `APP_MAIL_FROM` controls the sender. A bounded retry worker retains failed jobs for operator investigation. It is an at-least-once delivery mechanism: a worker crash after SMTP succeeds can produce a duplicate email, while token consumption remains single-use.

Without `SMTP_HOST`, local development mail is written to `APP_MAIL_OUTBOX_DIR` (default `./var/mail-outbox`) as UUID-named `.eml` files. Inspect those files directly to follow invite/reset links. The directory is never served by an HTTP endpoint. It contains secret activation/reset links: keep it outside static hosting, restrict its filesystem ACL to the developer/service account, and delete old local messages. Plaintext queued message bodies are cleared after successful delivery; stored invitation/reset tokens are hashes. Responses never contain the tokens. Existing users accepting another tenant's invitation must supply their current password, preventing invitation-based account takeover.

User emails are globally unique shared identities. A selected active membership determines the session's tenant; `tenantId` on login may select only an existing active membership. Platform accounts are isolated from organization records. Predefined roles are ADMIN, HR, MANAGER, MEMBER, AUDITOR, SALES, PROCUREMENT, FINANCE and PAYROLL. Custom roles are server action allowlists capped by a predefined non-admin role; current tenant/object checks still apply. TOTP MFA, single-use recovery codes, password history, session rotation and revoke-all are implemented; SSO is not. Tenant suspension blocks protected access and revokes sessions. The last active organization administrator cannot be deactivated or demoted, including simultaneous requests. Anonymous reset responses do not disclose whether an email exists.

Public company registration requires email proof before any company or owner is created. First-run installation must already be complete. Domain claims require an exact expiring DNS TXT challenge. Session refresh rotates the opaque cookie and invalidates its predecessor while preserving a 24-hour absolute lifetime; it is not an OAuth grant. Login outcomes are persisted with hashed email/IP identifiers, and active sessions include informational user-agent metadata.

Organization administrators can upload a logo through `POST /api/v1/org/logo` with a base64 `dataUrl`. Only PNG, JPEG and WebP bitmap content is accepted, checked against its declared type and magic bytes, limited to 512 KB and 4096 Ã— 4096 pixels. SVG, HTML and remote image URLs are rejected. Files use generated tenant-owned names under `APP_LOGO_DIR` (default `./var/logos`); keep this directory writable only by the service account and outside static hosting. `GET /api/v1/org/logo` requires an active tenant session and always resolves that tenant's stored logo. The public profile reference is `/api/v1/org/logo`; internal filenames are not sent to the browser. Profile updates preserve this reference. Replacement removes the old file after transaction commit; rollback removes the new file. Include logo storage in the backup/restore plan.

`GET /health` checks database connectivity without returning configuration or tenant information. `GET /api/v1/me` returns the current principal. Admin lists support `page`, `size` (maximum 200) and user/tenant searches support `q`. The organization directory exposes names, emails and membership roles only; private HR data is handled separately by the workforce controller. Audit history is limited to ADMIN/AUDITOR. Accounts see only their own recent events on the member dashboard.

Workflows publish immutable versions and start independent approval instances. A step can require any or all assigned approvers; amount conditions skip non-applicable steps. Overdue steps are reassigned once to independent active organization administrators, preserving the step's ANY/ALL quorum. Requesters never approve their own cases. Delegations and decisions retain history. Typed form mappings support bounded text/numbers, ISO dates and approved select options; reserved identity/permission fields and unknown input keys are rejected. A dry-run validates the editable draft without creating an instance. New cases use the immutable published schema. Reviewers can request changes; requester resubmission creates a linked new instance on the original published version while preserving the old audit history. These generic approvals do not automatically post a domain expense, purchase order or payroll; those domains retain their own guarded actions.

Documents use `APP_DOCUMENT_DIR` outside the relational database. Accepted formats are PDF, PNG, JPEG, WebP and UTF-8 TXT/CSV, capped at 5 MB. Configure `APP_CLAMAV_HOST` and optional `APP_CLAMAV_PORT` for real ClamAV INSTREAM scanning. Otherwise files remain quarantined until a different authorized administrator/reviewer supplies a manual verdict and evidence. A manual verdict is not a malware-free certification. Versions preserve checksums; retention dates and legal holds block deletion. Downloads recheck tenant and linked-record visibility. Expiring links remain authenticated and user-bound. The authenticated preview endpoint delegates the same current access, quarantine and integrity checks, then returns a sandboxed inline PDF/image or plain-text response with no-sniff headers. A configurable S3-compatible blob adapter is available; each version records LOCAL or S3 so existing local documents keep their original backend.

Report snapshots contain authorized rows and expire after seven days. CSV export escapes spreadsheet formula prefixes, preserves row manifests and rechecks current source access on download. Saved schedules revalidate the owner's active role when they run. A scheduled worker failure is recorded as a failed export; operators can rerun the saved definition. A process crash between claiming a schedule and generating it can skip that occurrence, so this scheduler does not claim exactly-once execution. XLSX/PDF report exports and arbitrary report builders are not implemented.

In-app notifications are persisted per user, with preferences, delivery history, announcements and same-tenant SSE updates. Task comments recognize @{UUID} or @email mentions and optional explicit recipients; every recipient must currently access the project under both their base and custom role. Previously stored mention content is rechecked on inbox, SSE and digest delivery after project access changes. Opt-in periodic digests queue at most 100 own unread unsent notices per occurrence and store delivery-item receipts to prevent duplicate digest items. The digest job records real queued/empty outcomes and correlates its mail job status. Transactional emails use the existing mail outbox. Outgoing webhooks contain event metadata only, use HMAC-SHA256 signatures, bounded retries and an operator allowlist `APP_WEBHOOK_ALLOWED_HOSTS`. Only public HTTPS endpoints on port 443 are accepted; redirects and private addresses are rejected. Configure allowlisted hosts before registering outgoing endpoints. Inbound metadata webhooks require the signing secret, `X-EOS-Event-Id`, `X-EOS-Timestamp` (within five minutes), and `X-EOS-Signature: sha256=<hex>` over `timestamp + '.' + raw_body`; event IDs are replay-protected. This exact signed route does not use cookie authority. Scoped read API credentials are hashed, expiring, revocable and rotatable. Their creator's current membership and permissions still apply. The current per-credential rate limiter is process-local.

Platform plans enforce active seats, pending invitation reservations, selected module writes and main-record quotas. Assigned subscriptions can be active, trial, suspended or cancelled, with explicit expiry/grace dates. Expired/suspended subscriptions retain readable records and block organization mutations. No assigned subscription means unrestricted baseline access until the platform administrator assigns a plan. Downgrades retain data and block further creation when over quota. Billing records are manual; no payment is charged. Operational screens record incident, backup, security review, UAT, defect and release evidence; they do not perform deployments or certify compliance. A recorded severe open defect or failed UAT case blocks a recorded release approval.

Review the phase policy decisions, action-level permission matrix, email sender, deployment secrets, retention, expected workload and recovery objectives before production. The root launcher, CI and encrypted backup utility supply local operational procedures, not a guaranteed SLA. Country-specific payroll/tax assurance, full accounting, external vendor mappings, arbitrary custom workflow scripts and AI remain outside the implemented baseline.

Own dashboard preferences persist up to twelve metric, chart or list widgets over supported authorized data sources. Source permissions are rechecked when data is loaded. Organization module flags are enforced on API reads and mutations, separately from subscription and role permissions; an administrator can re-enable a disabled module. The deal-conversion report uses actual lead/current opportunity outcomes for the selected creation-date range, respects sales ownership/team access, and keeps won amounts separated by currency. It does not claim historical transition-cohort timing.

Optional object storage uses `APP_OBJECT_STORAGE_ENDPOINT`, `APP_OBJECT_STORAGE_BUCKET`, `APP_OBJECT_STORAGE_REGION`, `APP_OBJECT_STORAGE_ACCESS_KEY`, `APP_OBJECT_STORAGE_SECRET_KEY`, and optional `APP_OBJECT_STORAGE_SESSION_TOKEN`. The application performs bounded path-style PUT/GET/DELETE with signed payload hashes and [AWS Signature Version 4](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/sig-v4-header-based-auth.html). No bucket or external account is created. HTTPS is required; `APP_OBJECT_STORAGE_ALLOW_HTTP=true` is an explicit local-development opt-in for a private test service. Keep the bucket private, enable encryption at rest, and scope the service identity to only necessary object operations on that bucket; review the [S3 security guidance](https://docs.aws.amazon.com/AmazonS3/latest/userguide/security-best-practices.html). Temporary credentials are supported through the session token; refresh credentials through the deployment configuration before expiration. Provider storage, request and transfer charges are separate operating costs.

The SigV4 unit test checks the published signature vector, and the default local adapter is covered by real document tests. No configured external S3/MinIO service has been round-trip verified in this workspace. Local encrypted backup captures LOCAL document bytes only; configured S3 versions require a separate provider bucket backup/versioning and recovery procedure. Database metadata alone does not back up remote object bytes.
